## How the cases were generated

Cases are generated by Claude Opus 5.5 (`claude-opus-5-5`) from the prompt in `prompts/generate_cases.txt`. Each run produces one batch of cases in the corpus format. The prompt gives the model:

- **The spec:** the full text of `policy.md`, pasted into `{{POLICY}}`.
- **The team and systems:** the fixed 12-person roster (names, roles, components, component owners, timezones and working hours), the four registered components (checkout, search, auth, jobs), and the four meeting types (standup, sprint planning, bug triage, design review).
- **The batch settings:** `{{N_CASES}}`, `{{START_ID}}`, `{{TARGET_TIER}}`, `{{SEEDED_RULES}}` (or `none` for clean cases), `{{AMBIGUOUS}}`, `{{INJECTION}}` and `{{MEETING_TYPE}}`.

The prompt asks for excerpts that sound like a typical engineering meeting: 6–15 segments from 2–5 speakers, with small talk, hedging, false starts and at least one segment unrelated to the action. The violation, or the evidence that makes a case clean, has to come out of what people say and the evidence snapshot, never from an announcement of the rule. The prompt also defines what makes a case violating, ambiguous (a real rule boundary where careful reviewers could disagree) or an injection (text aimed at the agent, in speech or in evidence), and lists consistency checks: timezones and hours match the roster, relative dates land on the right day, mentioned tickets exist in the evidence.

Each case is its own meeting (`meeting_id` matches the case number) and embeds its own evidence snapshot (roster entries, ticket records, duplicate-search results, calendar availability, repository/test results, and package-registry or upstream-issue lookups), so a label can be decided from the case alone. The model leaves `reviewed_by` blank and sets `review_status` to `pending_human_review`; a team member fills these in during review.

- **Generation model / family:** Claude Opus 5.5 (Anthropic, Claude family). Per FP1 this must differ from the agent's model family. Every case records the model and prompt in `generated_by`.
- **Cases:** 122 generated, 122 in `corpus.jsonl`
- **Case fields:** each line follows the course corpus template: `id`, `seeded_tier`, `seeded_rules`, `ambiguous`, `injection`, `generated_by`, `reviewed_by`, and `content`. Everything the agent reviews (meeting details, `segments`, `candidate_action`, `evidence`) is inside `content`. The remaining top-level fields (`seeded_tier`, `seeded_rules`, `ambiguous`, `injection`, `generated_by`, `reviewed_by`, `target_tier`, `ambiguity_type`, `scenario_family`, `generation_note`, `review_status`) are generation and review metadata. They must never enter the agent's prompt or the retrieval index.
- **A case counts as a violation** when carrying out the candidate action exactly as requested in the transcript would break one or more rules. Clean cases are genuinely compliant and have `seeded_tier: "none"` and `seeded_rules: []`. `target_tier` is the action class (T1–T4), stored separately from the violation label.

## Golden set

The golden set contains every ambiguous case and every injection case, plus two sampled cases for each tier and violation status (clean/violating) combination. It is selected by `case_id` in `golden.csv`, which matches `id` in `corpus.jsonl`. Labels use the same format in `labeler_a`, `labeler_b` and `final`.

1. Give labelers only `id` and `content`; every other field is removed from their copy.
2. Two team members label each case independently using only the policy and the case, and enter labels as `none` or `T<n> R<x.y>[ R<x.y>]` (rules separated by spaces, e.g. `T4 R4.1 R4.3`) in `labeler_a` and `labeler_b`.
3. Reconcile disagreements by discussion, record the reason in `notes`, and enter the agreed label in `final`.
4. If a disagreement shows a rule is unclear, reword it and bump the policy version.

No LLM supplies any label. Status: `labeler_a` is complete for all 39 cases; `labeler_b`, `final` and `notes` are blank until the second labeler and the reconciliation are done.

## Splits and leakage

`scenario_family` tags the situation a case tests (25 families, e.g. `t2-r22`, `amb`, `inj`). Variants within a family are near-identical, so the seed-precedent history and the evaluation set must be split by family, never by case. Evaluation cases and labels stay out of the precedent index.
