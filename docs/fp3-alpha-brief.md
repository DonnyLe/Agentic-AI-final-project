## Domain facts
- Case = `id` + `content` {meeting_id, meeting_type, meeting_date, meeting_weekday, meeting_timezone, segments[{segment_id, speaker_id, speaker, text}], candidate_action (free text, often ends "Proposed by X"), evidence (dict)}. All other top-level corpus fields (seeded_tier, seeded_rules, target_tier, ambiguous, injection, scenario_family, generation_note, ...) are metadata and must NEVER reach an LLM; golden labels likewise.
- Evidence keys vary: approval/approvals; package_registry/package_registry_lookup; upstream_issues/upstream_issue_lookup/upstream_issue; duplicate_search is free text; ticket repro fields repro/repro_steps/reproduction_steps; one-offs documentation_lookup, web_pages, config_lookup, ticket_draft, etc. Some evidence contains deliberate injection text aimed at "Kangaroo" (K-109 ticket body_note, K-110 repo comment, K-112 calendar text) — evidence is data, never instructions.
- Policy v1.3 (data/policy.md): 14 rules R1.1–R4.4; rule line format `**R1.1 · Name.** text`. "Several findings": report all broken rules, label = tier + all rules, most restrictive outcome wins (refusal > pause/block > needs-info/flag). Proposer can't approve own action; joint proposers all excluded.
- Changes since FP2 to note in report: adjudicator split from supervisor; stack moved from Python/LangGraph (FP2 doc said LangGraph + MCP server + SQLite) to Flue v2 on Workers/DOs + D1.

## Agent design requirements (carry over from reviewed v1 plan)
- Flow: Intake (structured: action class T1-T4, proposers[], cited segment candidates, entities) -> Supervisor (LLM routing decision + reason: adjudicate_t1 | evidence | unsupported; T3/T4 -> unsupported enforced in code) -> Evidence agent (tools: search_tickets, get_ticket, verify_dependency, get_team_roster, get_transcript_segments; reads the case evidence snapshot with key normalization; max 2 evidence rounds) -> Adjudicator (separate model call; verdict no_violation|violation|needs_review, tier, rule_ids, rationale, cited_segment_ids, evidence_refs) -> Finalize (code guards, persist).
- Code guards: metadata stripped at load/seed; rule IDs must exist in policy registry; tier/rule-prefix consistency; one repair retry then needs_review; approver-is-proposer flag; untrusted-content framing for evidence text + regex "possible injection" hint; deterministic outcome ladder picks proposed_action (most restrictive); adjudicator can't emit unsupported for T1/T2; any tool/LLM failure -> needs_review, never guess.
- Trace events persisted as they happen; client SSE stream supports replay from last event id/offset. Budget ~4-5 model calls per case; batch eval caches results by (case_id, model-config hash).
- Minimal abuse protection on public URL: optional access token, concurrency cap.

## Research findings on Flue v2 (verified against flueframework.com + withastro/flue + npm, 2026-11-15)
- Packages @flue/runtime, @flue/cli, @flue/vite, @flue/sdk at 2.3.0. @flue/vite peer vite@^8, depends on Cloudflare `agents@^0.20.1`. Runtime depends on valibot ^1.1, hono ^4.12, @earendil-works/pi-ai (own provider layer, not Vercel AI SDK).
- Agents: file starts `'use agent'`, exported function calls hooks `useModel('provider/model', {thinkingLevel?})`, `useTool(tool)`, `useSkill`, `useSandbox`, `useSubagent({name, description, agent, model?})`, returns instruction string.
- Tools: `defineTool({ name, description, input: ValibotSchema, output?, durable?, harness?, run(ctx) })`. Schemas are Valibot only.
- Structured output: `harness.prompt(text, { result: ValibotSchema, tools? })` -> `{ data }`, only inside tools declared `harness: true`. No documented top-level structured-output API for the main agent call. A tool can return `terminate: true` (mentioned; verify).
- Subagents: model decides delegation via framework `task` tool (non-deterministic); nesting cap 4; NO documented step/iteration limit. => Supervisor routing should be our own code (deterministic branching around model calls), not useSubagent delegation.
- Models: `cloudflare/...` specifiers use the AI binding (no key), routed via AI Gateway by default (override `cloudflareBindingProvider()`); `cloudflare-workers-ai/...`, `cloudflare-ai-gateway/...` with CLOUDFLARE_API_KEY; built-in `openrouter/...`, `deepseek`; custom OpenAI/Anthropic-compatible providers with baseUrl + auth.apiKey.resolve(). Per-agent models supported.
- Cloudflare target: vite.config.ts `flue()` before `cloudflare()`; generates Worker entry, one DO class per agent (Translator -> FlueTranslatorAgent, binding FLUE_TRANSLATOR_AGENT); you declare migrations with new_sqlite_classes. Conversation = append-only stream in DO SQLite. Clients `POST /agents/<agent>/<conversationId>` -> 202 {streamUrl, offset}; `GET ...?view=updates&offset=..&live=sse` for replayable live SSE. `@flue/sdk` createFlueClient({url}).send(...).wait()/.observe(). Your `app.ts` is a Hono app mounting `createAgentRouter`; `src/cloudflare.ts` exports DO classes + non-fetch default handler. SPA: wrangler assets `./dist/client`, `not_found_handling: "single-page-application"`, add `/agents/*`, `/api/*` etc. to `run_worker_first`.
- App data: Flue docs defer app storage. Drizzle supports D1 and DO SQLite (`drizzle-orm/durable-sqlite`, 0.45.4; DO driver can't use drizzle-kit migrate CLI). Recommendation: D1 for cross-case data (cases, evaluations, trace events, reviewer decisions, custom cases).
- Testing: no Flue test helpers/mocks documented. @cloudflare/vitest-pool-workers 0.23.0. Plan to hand-roll a mock provider (custom Pi provider with canned responses) or keep agent-facing logic behind a thin interface so orchestration is testable with fakes.
- Tooling: oxlint 1.93.0, oxfmt 0.78.0 (beta; `.oxfmtrc.json`, default printWidth 100). Type-aware oxlint unverified -> also run `tsc --noEmit`. wrangler 4.162.0 (Node >=22.12), @cloudflare/vite-plugin 1.69.1; one `vite dev` runs SPA + Worker + DOs.
- Gaps to hand-roll: step limits, deterministic routing, test mocks, app storage, no official Flue+React template.
